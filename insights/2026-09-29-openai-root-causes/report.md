# OpenAI 事故根因、故障模式与技术方向

分析日期：2026-09-29。面向架构、平台和可靠性工程决策。

**核心判断：[推断] 已披露复盘反复呈现“变更或维护触发 → 共享依赖失效 → 重试、缓存或自动化扩大影响 → 恢复阶段再次受阻”的链条。工程优先级应放在变更安全、故障隔离和可验证的恢复能力，同时把模型输出、任务完成和数据完整性纳入可靠性。**

范围：沿用现有 OpenAI 服务可靠性数据，讨论 API、ChatGPT、Codex 及相关依赖；不扩展为模型越权或 AI 安全事件研究。统计冻结于 **2026-09-26 22:51:22 UTC**；在线核验用于验证选定复盘，不把新增记录混入分母。事实指官方自述，推断指本报告跨案例归纳，建议指待验证的技术设计。

### 三条尤其值得深入的链条

**控制面故障会剥夺自救能力（S1、S3）。** [推断] 风险不止是“监控服务负载太高”或“网络升级失败”，而是故障修复所需的操作也穿过同一失效依赖。仅增加普通容量，无法保证事故中仍能回滚、隔离坏实例或修复主机网络。需要单独验证恢复通道可达性。

**保护和恢复动作也会生成新故障（S6、S8、S10）。** [推断] “熔断器解除”“配置已回滚”“路由恢复”都是中间状态。过时调度计划批量执行、自动发布重放坏配置、回流骤增，都可能造成第二轮失败。恢复必须包含队列重算、坏版本阻断和受控引流。

**业务控制链故障可伪装成模型服务问题（S4、S7、S13）。** [推断] 用户看到 429、403 或功能消失，不足以定位到 GPU、余额或权限策略本身。需要沿“认证 → 权限 → 配额 → 路由 → 调度 → 推理 → 回传”追踪失败位置。单凭状态码加大重试，可能既无效又放大故障。

## 3. 七种可复用故障模式

这些是机制分类，**不是互斥的事故计数类别**；同一事故可以同时出现几种模式。

| 模式 | 系统性薄弱点[推断] | 可观察到的验证信号 | 对应案例 |
|---|---|---|---|
| 变更破坏仍在运行的系统 | 配置语法通过，但与旧版本、旧权限或旧路由不兼容 | rollout 阶段旧实例错误率；有效路由或授权集合减少；坏版本被重新下发 | S1、S8、S10、S13、S14 |
| 共享依赖扩大故障范围 | 多产品共用身份、连接、配置或数据库，一次局部变化跨产品传播 | 多产品同时异常且共同依赖饱和；故障边界大于发布单元 | S1、S5、S7 |
| 容量下降与重试构成正反馈 | 请求失败增加额外请求；恢复流量超过恢复中的服务承载力 | attempts/逻辑请求比上升；连接池等待和队列年龄增长 | S5、S9、S10 |
| 自动控制系统使用过时状态 | 执行动作与决策时状态脱节，保护解除后批量补执行 | 队列计划年龄；同批调度撤下的引擎数；状态版本不匹配 | S6 |
| 有冗余但不能及时接管 | 数据副本、备用资源与可执行切换流程之间存在缺口 | 切换依赖人工；恢复接口不可达；冷启动或下载排队 | S1、S2、S3 |
| 端到端正确性漏检 | 模型能响应、后端完成、前端可见、权限正确各自独立 | 语义质量退化；JS 加载失败；允许/拒绝测试不一致 | S11、S12、S13 |
| 静默数据丢失 | 数据生成、持久化、投递、可查询未闭环验证，观测与业务同故障 | 事件量异常减少；写入与读取对账不一致；历史不能回放 | S14 |

  A[配置 / 发布 / 维护 / 供应商异常] --> B[路由、身份、数据库、网络或调度失效]

  C --> D[重试与连接压力增加]
  D --> B
  C --> E[开始恢复]

## 4. 技术方向：先阻止扩散，再缩短完整恢复时间

以下均为[建议]，是从案例推出的设计和验收方向，不代表 OpenAI 已部署这些能力。P0/P1 是本报告建议的先后顺序，实际排序要用自家失败成本和测量结果调整。

| 优先级与方向 | 具体工程工作 | 如何证明有效 | 依据 |
|---|---|---|---|
| **P0：配置与数据迁移安全** | 类型/schema 校验之外，验证服务版本兼容、旧路由保留及权限变化；按故障域灰度；限制回填目标集；回滚同时写入持久的坏版本阻断 | 在旧新版本共存、缓存过期后做旅程测试；注入坏配置，证明它只能影响一个灰度单元且不会被自动重发 | S8、S10、S13、S14 |
| **P0：依赖隔离与负载准入** | 对产品、区域、租户和后台活动设置并发/连接配额；给在线请求保留资源；统一端到端 retry budget；退避、抖动和负载丢弃 | 移除一个副本或限制网络资源，观察健康单元成功率、连接等待、重试放大系数是否保持在事先约定范围 | S5、S7、S9 |
| **P0：独立恢复通道** | 管理与业务流量隔离；给控制面保留容量；准备不依赖失效 DNS/调度入口的回滚、主机修复与接管路径 | 演练控制面不可用和区域丢失，实际完成回滚/切换；记录请求恢复、任务恢复和数据补齐三个时间 | S1、S2、S3 |
| **P1：调度决策新鲜度与安全解冻** | 对容量操作记录状态版本/有效期；解冻时重新规划、合并或丢弃过时动作；限制同批退出的服务容量；分批恢复 | 人为暂停调度，期间改变流量和容量，再恢复，验证不会执行过时的批量缩容；正常负载与故障恢复分别压测 | S6、S10 |
| **P1：推理正确性验证** | 按模型、kernel、GPU、驱动及精度组合做差分测试；覆盖多语言、结构化输出与工具调用；上线后监测语义异常 | 除 HTTP 指标外，验证输出解析率、数值差异容限、异常文本率及分层质量回归；阈值用稳定版本基线制定 | S11 |
| **P1：用户任务与数据完整性** | 将启动、执行、断点、产物持久化、读取、UI 展示串成成功条件；关键事件可重放、可对账；独立检查日志量下降 | 注入断网、进程重启、日志投递失败；核对任务及事件缺失、重复和权限错误；确实没有日志时显示未知或失败 | S9、S12、S13、S14 |

### 最值得投入的三个研究问题

1. **状态感知的变更验证。** [建议] 把配置、二进制版本、权限和路由依赖纳入同一变更模型，提前检查“增加一个服务却移除旧服务访问权”这类非局部效果。先用历史事故回放评估规则覆盖与误报，再考虑模型辅助变更评审。
2. **面向恢复过程的容量控制。** [建议] 把恢复中的连接数、任务积压、模型就绪速度纳入引流控制；比较固定限流与自适应准入，在相同故障注入条件下的二次过载次数、任务成功率和完整恢复时间。公开材料不足以给出一个通用最优参数。
3. **Agent 任务可靠性。** [建议] 将一次长任务作为测量单位，研究步骤级检查点、受控重放、幂等提交和外部副作用核对。仅成功生成 token 无法保证任务最终交付；但本次复盘也没有证明 OpenAI 所有任务都缺少上述机制。

[假设] 如果本团队也存在类似共享依赖和自动化恢复链，P0 三项会比单独提升错误分类精度更直接地降低故障损失。验证方式是先用本团队历史 trace 和演练对比，而不是把这个排序当作已测得的投资回报。

## 5. 对使用 OpenAI 的应用与 Codex 工作流意味着什么

[建议] 接入方应把“真实配额不足”“依赖故障造成错误限流”“暂时过载”分开处理：结合错误正文、请求 ID、账户状态和时间相关性，不能看见 429 就无限重试，也不能假设换模型一定绕过共享身份或路由故障。

[建议] 给长任务保存应用侧 task ID、阶段进度、输入引用、结果与外部写入状态。重试前核对副作用；提交失败或连接中断时，不自动假定远端没有执行。对高价值任务采用检查点和有预算的重试，记录“从用户发起到产物可读取”的完成率。

[建议] 备用路径应通过真实演练核验模型兼容性、身份、配额、数据和网络依赖。API key 可能绕过某条账号登录路径，却不能保证绕过共同推理或基础设施故障；跨供应商切换也有输出、工具协议、数据治理和成本差异。

## 6. 反面观点、风险与我可能错在哪

- **披露偏差。** 较复杂或影响广的事故更可能有复盘；这些案例的机制不能代表全部事故分布。容量、供应商或模型质量问题的总体占比仍未核实。
- **共同机制不代表相同内部根因。** 同样写“配置问题”，可能分属不同系统；本报告不能证明同一组件反复出错，更不能归因为个人失误或组织文化。
- **来源不是独立取证。** 公开复盘是厂商选择披露的叙述；内部证据可能改变触发、放大因素与优先级判断。
- **隔离和冗余有成本。** 热备与分区会降低资源利用率、增加协调复杂度；多云并不能自动消除身份、数据或发布系统的共同依赖。应按关键旅程选择故障域与恢复目标。
- **灰度并非充分条件。** 若不覆盖大规模拓扑、低频操作、缓存失效和旧新版本混跑，灰度仍会漏检 S1 一类问题。
- **不推算不可靠的时间指标。** 2025-07-15 复盘存在回滚早于影响起点的时间线冲突；2026-03-11 记录正文写 2025 年；2025-10-02 权限复盘的“首小时修复”和后文时间也不一致。这些不用于计算检测/修复耗时。审计日志只知从 2025 年 11 月拆分时引入，不能补造精确开始时刻。
- **没有更新可用性结论。** 本次没有重算或改写旧报告的故障区间、可用性、SLA 或线上现状；`resolved` 不等于历史数据已全部恢复。

## 7. 可执行的下一步

[建议] 首轮验证用四个演练回答四个问题：坏配置回滚后会不会自动重发；去掉一个数据库副本后重试会不会放大；调度暂停再解除会不会重放过时动作；业务完成后能不能找回任务产物与审计事件。先记录基线，再分别加入保护措施对比，阈值由业务容忍度制定。

尚缺的关键证据：内部依赖拓扑、按产品/模型/区域分层的请求与任务指标、实际故障域大小、完整恢复时间、复盘改进项的上线与演练记录。获得这些数据后，才能从案例归纳进一步做根因占比、损失贡献和投资优先级的定量排序。

复算方式及输入来源见 [README.md](README.md)；76 条提取后的冻结复盘正文见 [writeups.json](analysis/writeups.json)。
